### 结论先行

这个项目的抽取架构**已经把开源信息抽取领域的核心思想实现了大半**，而且有两处比开源同类项目更严谨：evidence 必须原样照抄否则整条丢弃（`Extractor.kt:14-16, 265-291`）——即学术上的 anti-hallucination grounding；以及「解不出返回 null，绝不猜」（`SpokenDate.kt:35`、`LocalExtractor.kt:17-23`）。**本次审计最重要的发现是一个被旧版两份报告都漏掉的实测错误值**：`LocalExtractor.amountOf()` 的金额正则只吃阿拉伯数字且不认单位倍率，`"花了一千二"`、`"花了三百多"` 抽不出来，而 `"花了 3k"` 会**抽出一个错到 1000 倍的 `3.0` 元并标成「非概数」**（即一个高置信的错误值）。这是本次唯一一条「已经在数据里写错了数字」的缺陷，而它的修法只动 `LocalExtractor.kt` 一个文件、零新增依赖，所以列在 P0 第一位。

真正还差的最后一步是三件事：**（1）本地确定性解析该接的还没全接上**（日期解析已经接进本地通道，但没接进模型通道做交叉校验——而项目自己的上游 `contract.md:90` 早就把 `<记录 uuid>#<序号>` 定义成「幂等去重键」，这正是当下 `merge*` 用模型生成的 `summary` 当键的病灶）；**（2）提示词字段说明 / 示例 JSON / 解析器是三处手工同步**，缺一个能一处声明三处派生的单一源；**（3）evidence 只定位到「哪条记录」且用 `firstOrNull` 取首个命中**，同文本记录会张冠李戴，且生日类的「最长公共子串 ≥ 6」缺一道密度闸门——六个字散落在一大段噪声里也会被认。

## 三、分级建议

每条固定四段：现状 → 缺口 → 改法 → 收益。**能给阈值就给阈值。**

### P0：改动最小、收益最直接

#### P0-1 让本地金额解析认中文数字与单位倍率（本次唯一「已经在写错数字」的缺陷）

- **借鉴自**：Duckling `Duckling/Numeral/ZH`（`一百二`、`1.5万` 的口语归一）与 jionlp `money_parser` 的「先做数值归一、再判上下文」两段式；以及小米 duckling 的**单位倍率**处理。
- **现状**：`sync/LocalExtractor.kt:50-71`。三条金额正则的捕获组**一律是 `\d+(?:\.\d{1,2})?`**（`:50,51,52`），即只吃阿拉伯数字，且**没有 `万/千/百/K/M` 单位**。
  ```kotlin
  private val SPEND_AFTER = Regex("""(花|付|交|充|消费|订)[了掉]?\s*(\d+(?:\.\d{1,2})?)""")   // :50
  private val MONEY_UNIT  = Regex("""(\d+(?:\.\d{1,2})?)\s*(?:元|块钱|块|毛|角)""")             // :51
  private val ESTIMATED   = Regex("""(大概|大约|差不多|左右|估计|不到|上下)""")                   // :55
  ```
- **缺口**：**已实测复现**（用同一套正则跑样本，非推断）：

  | 原话 | 现状行为 | 应为 |
  | --- | --- | --- |
  | `花了 3k` | ✅命中，但金额 = **`3.0` 元**、`estimated=false` | 3000，且整条应保守跳过（`k` 不是中文口语） |
  | `1.5 万首付` | ✅命中，但金额 = **`1.5` 元** | 15000 |
  | `花了三百多` | ❌完全抽不出（`LocalExtractorTest` 无此用例） | 300 + `estimated=true` |

  3. **交叉校验**（这是本条的核心）：模型给了 `due` 且本地也解出来了 → **两者相等则照用，不等则用本地值**（本地是确定性的），并记 `dueConflict = true`；本地解不出而模型给了 `due` → 保留模型值但同样记 `dueConflict = true`。

- **收益**：把「日期算错 → 提醒在错的日子响」这类**用户无法自查**的错误，变成「算错 → 按本地的对值落地 + 明确问一句」。可验证：构造 12-31 / 周日边界用例，断言 `dueConflict=true` 且 `due` 等于 `SpokenDate` 的值。**零新增依赖，纯本地函数复用。**

#### P1-2 把 evidence 从「哪条记录」升级到「记录 + 序号」，并给生日类补密度闸门

- **借鉴自**：LangExtract 的**事后对齐**三件套——精确匹配 → **保序 DP 解决重复提及**（`_select_monotonic_matches`，Pareto frontier + bisect）→ LCS 兜底 + **覆盖率 0.75 + 密度 1/3 双闸门**（`_accept_lcs_match`，作用原文是「rejecting scattered matches」）；以及本项目上游 `contract.md:90` 早已定义的 `source_ref = <记录 uuid>#<序号>`。
- **现状**：`sync/Extractor.kt:265-269`：
  ```kotlin
  private fun matchRecord(records: List<Record>, evidence: String): Record? {
      val needle = evidence.replace(" ", "").trim()
      if (needle.isEmpty()) return null
      return records.firstOrNull { it.text.replace(" ", "").contains(needle) }   // :268
  }
  ```
  生日类走另一条路（`:282-291`）：`text.contains(evidence.trim()) || longestCommonRun(text, plain) >= 6`。
  落地时只留 `record.time`（`:186, 198, 217`），**`Record.uuid` 被丢掉**——`Mention`（`data/People.kt:39-45`）只有 `date/time/personId/summary`，`ExpenseFact`（`:56-82`）同理。
- **缺口**：三个，逐个说清「为什么现在的写法会错」：
  1. **`firstOrNull` + 只比对文本 → 张冠李戴**：同一天两条记录文本相同（复制粘贴、或「又买了点东西」被改成一样的），第二条的 evidence 会**匹到第一条**，于是提及/支出挂到了错的时间点。上游 `contract.md:90` 的 `<uuid>#<序号>` 正是为「同一句话里的多笔账」设计的去重键，现在丢了。
  2. **密度闸门缺失 → 「六个字散落在噪声里」也放行**：`longestCommonRun(text, plain) >= 6` 只问「有没有连续 6 个字对上」，不问「这 6 个字占 evidence 的比例」。evidence = 30 字、只有中间 6 个字偶然对上，照样通过 → 生日被认错。LangExtract 的两道闸门是**覆盖率 ≥ 0.75**（`matches >= ceil(len * 0.75)`）**且密度 ≥ 1/3**（`matches / span_len >= 1/3`），后者专门治这个。
  3. **零宽字符/BOM 未处理**：现在只 `replace(" ", "")`，`str.strip()` 那类操作会保留零宽空格与 BOM（LangExtract 的 `_is_blank` 用 `_INVISIBLE_CATEGORIES = {Cc, Cf}` 专门处理）。语音输入/复制粘贴会带进来。
- **改法**：
  1. `matchRecord` 返回 `Triple<Record, Int, Int>` 或一个 `EvidenceSpan(recordUuid, start, end, occurrenceIndex)`——**evidence 在 record.text 里的字符偏移用 `indexOf` 就能拿到**（这也是 P1-2 顺带给出的能力：卡片可高亮原文）。
  2. 记录选择改为**在 `evidence` 的候选里按出现顺序分配**（保序，照 LangExtract 的 `_select_monotonic_matches` 思路）：同一个 evidence 文本匹配到多条记录时，按它们在当天记录序列里的顺序**依次**分配，而不是全给第一条。
  3. `Mention` / `ExpenseFact` / `Todo` 各加 `sourceRef: String = ""`（形如 `<uuid>#<序号>`，**默认空串，存量数据零迁移**），落地时填上（`SyncEngine.kt:626-641`）。
  4. `mergeExpenseFactsForDate`（`data/Expenses.kt:24-38`）与 `mergeTodosForDate`（`data/Todos.kt:181-198`）的去重键**逐步改为以 `sourceRef` 为主、`summary` 降为兜底**。这不是可选项：`Expenses.kt:34-36` 现在用 `fresh.map { it.time to it.summary }` 当键，而它自己的注释（`Todos.kt:174-176`）已经承认「模型换个说法是常事」——**拿模型生成的串当去重键，就是这个项目已经反复踩过的坑**（Actual Budget 的解法正是「匹配原始导入串而非用户改过的串」）。
  5. `evidenceFound`（`:282-291`）加两道闸门：覆盖率 `matches >= ceil(evidence.length * 0.75)`、密度 `matches / span.length >= 1.0/3`。**中文化适配**：LangExtract 的 `_normalize_token` 是「小写 + 去末尾 s」，**对中文无效**——按 CJK 逐字符切分即可，LCS 退化为字符级，**这恰好就是你生日类现在的做法**，所以只是加闸门，不改算法。
  6. `strip()`（`:294-295`）补上零宽字符过滤（`\u200B`–`\u200D`、`\uFEFF`）。
- **收益**：①同文本记录不再张冠李戴；②生日类误认（六个字散落命中的那类）被闸门挡住——**这是收紧，不是放宽**，与纪律 2 一致；③`sourceRef` 为「重抽幂等」提供不依赖模型措辞的稳定键，直接治 `Expenses.kt:34-36` 的病灶；④附带拿到字符偏移，界面能高亮原文那几个字。
- **改动面：中**（`Extractor.kt` 三个函数 + `People.kt`/`Todos.kt` 各加字段 + `SyncEngine.kt` 落地处 + `Expenses.kt`/`Todos.kt` 合并键）。
- **成本/风险**：零新增依赖，全部是本地字符串算法（`indexOf` + 朴素 LCS，项目已有 `longestCommonRun`）。**存量数据不迁移**（新字段默认空串，合并键在 `sourceRef` 为空时自动退回旧行为）。可逆：删掉新字段即回到现状。

#### P1-3 分类兜底从「猜不到就归其他」改为「保留空 + 本地关键词兜底」

- **借鉴自**：Actual Budget 的**「空条件 = 不匹配，而非匹配全部」**（官方文档原文语义）+ Firefly III 的 `has_no_category`（未分类＝**关联缺失**，不是往分类表塞特殊值）。
- **现状**：`data/ExpenseCategories.kt:25-34`：`text in ALL` 精确匹配 → 按 `/、，, - （ (` 切段再试 → **否则一律 `OTHER`（「其他」）**。本地通道 `LocalExtractor.kt:138` 直接 `ExpenseCategories.normalize(sentence)` —— 把**整句话**当分类输入。

  1. 新增本地关键词兜底表（`ExpenseCategories` 里加一个 `KEYWORDS: Map<String, List<String>>`）：`餐饮 ← 吃|饭|菜|餐|外卖|奶茶|咖啡`、`交通 ← 打车|地铁|公交|加油|停车|高铁|机票`、`居家 ← 房租|水电|物业|日用|超市`、`医疗健康 ← 医院|药|挂号|体检`、……**命中唯一一类才用，命中多类返回空串**。
  2. `normalize()` 的兜底**从 `OTHER` 改为 `""`**（＝未分类）；「其他」**只在模型明确输出「其他」时才产生**。**这会改变现有断言语义**：`ExpenseCategoriesTest.kt:22-24`（`normalize("吃饭")=="其他"`）要改成 `normalize("吃饭")=="餐饮"` 或 `==""`，`:196` 同理——**这些测试必须一起改，不能只改实现**。
  3. 提示词里给重叠分类加**优先级顺序**（不是改分类表）：如「能归 `订阅服务` 的一律归 `订阅服务`；能归 `人情往来` 的优先于 `餐饮`」。这一句直接抄进 `Extractor.SYSTEM:106-108` 的口径段。
  4. 空串的语义**与现在一致**（`People.kt:62-68` 的注释已经写清「空＝这份数据还没抽过分类」），所以统计口径（`data/Stats.kt:47` 的 `UNCATEGORIZED`）不用改。
- **收益**：本地通道从「不认人就完全不分类」变成能确定性归几大类；「模型给了怪名字」与「模型说其他」不再混为一谈（统计时能分别计数）。可验证：`normalize("吃饭")` 不再返回「其他」。
- **改动面：小**（`ExpenseCategories.kt` 一个文件 + 改 2 处既有断言 + 提示词一段）。
- **成本/风险**：零依赖。风险：**改 2 处既有测试断言**是行为变更，需在提交信息里写清「未分类从『其他』改为空串」以免被当成回归。

### P2：场景性收益，当前可缓

#### P2-1 结构化输出失败时重试一次（沿用「重试只用于格式错、丢弃仍用于证据错」）

- **借鉴自**：Instructor 的 reask 循环（**保留模型上一轮原响应**，再追加一条「上一次返回的不是合法 JSON，错误是 X，请只输出 JSON」的 user 消息；官方建议校验错 **2 次**、退避 **1s→10s**；官方明确只重试「解析错 + 校验错」，**不重启限流/网络错误**）。
- **现状**：`data/AiClient.kt:33-38`——`completeJson()` 解析失败直接抛 `AiException`；`sync/SyncEngine.kt:501-510` catch 到就 `continue`（跳过这一天、不标记完成、下次打开重试）。**`:489-493` 的注释已经把这个设计说清了，而且它是对的**：一天失败不该堵住整批。`AiClient.stripFence()`（`:101-108`）已经会剥 Markdown 围栏、取首 `{` 到末 `}`。
- **缺口**：只有「跳过等下次」一条路，代价是**反复计费**（`extractDue` 每次返回同一批最近几天，同一批请求每次冷启动原样重发）。**注意 `MAX_TOKENS = 2048`（`AiClient.kt:131`）** ——记录多的日子可能被**截断**成半个 JSON，重试能缓解但根因是上下文过长。
- **改法**：`completeJson` 解析失败时，**在同一次调用内**追加一条 user 消息（保留模型原回复）重试 **1 次**（不是 2 次——移动端流量/费用敏感，且你要挡的主要是偶发格式问题）；仍失败则照现在的逻辑抛错、由 `SyncEngine` 跳过。**不动 `SyncEngine` 的失败语义。**
- **收益**：只在「模型偶发输出坏 JSON」时才明显（预计是少数天数），主要收益是**少一轮重复计费**。**改动面：小**（`AiClient.kt` 一个方法）。
- **⚠️ 与纪律 1 的冲突与裁决**：**重试只允许用于「格式错」，绝不允许用于「evidence 对不上原文」**。evidence 校验失败时让模型改口＝引导它编一个能对上的引用，直接违反「宁可不输出也不猜」。**LangExtract 的做法不同**（它自带 `verify_quote_in_source` validator，校验失败会重发），那是**它的场景代价结构与你不同**；你这里维持「丢弃」是对的。

#### P2-2 日期与金额的「区间 + 时长」表达（当前只有单点）

- **借鉴自**：SUTime 的 `Range{begin, end, duration}` + 开区间端用 `TIME_UNKNOWN` 占位；小米 duckling 的 `OpenIntervalValue(start, direction)`；jionlp 六分法里的 `time_span` / `time_delta`。
- **现状**：`SpokenDate.parse()` 返回**单个 `LocalDate?`**（`:36`）。`月底` 被解析成「本月最后一天」（`:67-69`），`N 个月后` 是单点（`:55-58`）。
- **缺口**：三家开源实现共享的设计都是 **(start, end, grain)** 三元组，你只有单点。「月底之前」「这周末」「10 周之内」「每 5 分钟」这类表达没有落脚点——现在要么解析成单点（丢失区间语义），要么返回 null（`SpokenDateTest.kt:125-134` 的「国庆节前」正是后者）。**收益只在用户开始说区间时才显现**，当前可缓。
- **改法**：`data class DateRange(val start: LocalDate, val end: LocalDate?, val grain: Grain)`（`end = null` 即开区间，照 SUTime 的 `TIME_UNKNOWN`）；`SpokenDate` 新增 `parseRange()` 与单点 `parse()` 并存，`Todo.due` 暂时不变。
- **收益**：只在「月底之前做完」「这周末」这类表达出现时才明显。**改动面：中**；**当前可缓**——先攒真实语料看这类表达占比。

#### P2-3 抽取质量回归门禁（**需先攒料**）

- **借鉴自**：LangExtract 仓库自带的 `benchmarks/fuzzy_benchmark.py` 的 **oracle 四件套**——正例 / **模糊正例** / **散落正例** / **近失负例**，断言 `matched` / `token_interval` / **`char_interval`** / `matched_substring`，并记录 `git_sha` + 全部阈值 + seed；指标口径照 `seqeval`（MIT）的 entity-level P/R/F1，**映射时按 people/expenses/todos 类内分别算，避免平均掩盖**。
- **现状**：`ExtractorTest.kt`（323 行）钉的是一批**关键约束**（「含糊的生日一个字都不许输出」「证据对不上就丢掉」），`LocalExtractorTest.kt:122-143` 甚至收了一批**真机漏进来的原文**——这部分做得相当好。但那是**断言提示词措辞与边界**，不是「真实语料 → 期望抽取结果」的评测集；全仓**没有任何 corpus 文件**（已确认无 `*corpus*`）。
- **缺口**：改一次提示词，无法量化回答「准确率是升是降」。**而且：grounding 只防编造、不防遗漏**——模型没写出来的人/钱，evidence 校验根本不会触发，这类漏抽当前完全不可见。
- **改法**（三步，都不引依赖）：①把 `LocalExtractorTest` 里那批真机原文 + 自己的历史记录抽 100–300 条 `(原文, 期望 people/expenses/todos, 期望 amount/estimated/due)` 三元组，落成 `app/src/test/resources/corpus/*.jsonl`；②写一个跑 corpus 的测试，输出 **entity-level P/R/F1（分类内）+ `estimated` 二分类准确率 + `due` 完全匹配率 + evidence 命中率**；③**evidence 命中率单独统计**（「模型给了 evidence 但对不上原文」的比例）——这是你已有的最强防线的**唯一观测指标**，现在没有任何数字。
- **收益**：**属于 P3 性质但用 P2 列出**——它要**先攒料**（现在没有 corpus），否则谈不上有收益。**不是不重要，是前置条件未满足。** 攒满之前，改提示词只能靠 `ExtractorTest` 那几条断言兜着。
- **改动面：中**（新增 corpus 文件 + 1 个测试类）。**依赖：先攒够 100 条以上真实语料。**
- **可顺带白拿的东西**：jionlp 官方 wiki 那张「**不支持清单**」（`二十来天`、`40来年前`、`前两天`、`10周之内` 明列「暂不支持」）**直接转成负例表**——它证明中文概数是**跨域公认难题**（jionlp 在时间域明确不支持 `N来`/`N几`），所以 `三百多` 抽不出来不是本项目没做好；同时这些负例正好对齐「解不出返回 null」的纪律，是现成的测试素材。

> **本报告未列 P3**：P2-3 已经是「需先攒料」的性质，不再单列一级。

## 四、⚠️ 不要照做的提醒

**运行时/体积权衡（本项目的硬约束：原生 Android / minSdk 26 / 无自建服务器 / 离线优先 / `isMinifyEnabled = false` 且 `isShrinkResources = false`，`app/build.gradle.kts:41-42`）**：

- 当前依赖只有 okhttp + kotlinx.serialization + Compose（`app/build.gradle.kts:88-104`），release 包 11.3 MB。**任何重型库都会直接顶在包体积上，且因为没有开 minify/shrink，连「R8 帮你裁掉没用到的部分」这条退路都没有。**
- **`.build/` 里有 Python 与 Node（`tools/*.mjs`、`tools/make_version_json.py` 在用），但那都是构建期工具，产物不进 APK** —— 这正是「挪到构建期/tools 目录」这条替代路径的**现成基础设施**，任何「想先验准确率」的重型方案都该先落在 `tools/` 里。

**否决表**

| 项目 | 为什么不引入 |
| --- | --- |
| **SUTime / CoreNLP** | **GPL-3.0**（copy-left）——分发即要求整个 App 随 GPL 开源，与「公开版无账号无服务器」的定位直接冲突；且需 Joda-Time + models jar，仓库 ≈405 MB |
| **HeidelTime** | **GPL-3.0**，且 `pushed_at` 2023-04-16（近三年半无提交）——保鲜闸 + License 闸双命中 |
| **hledger / Beancount** | **GPL 系**；且复式记账的五个根账户本项目不需要 |
| **Firefly III** | **AGPL-3.0**（copy-left 最强档）。它的「去重指纹不可含用户可编辑字段」这个洞察值得抄，**代码一行不能进** |
| **cocoNLP** | **无 LICENSE 文件**（`license: null`）＝默认保留全部权利。**比 GPL 更该直接排除——连读它的测试用例作参考都不建议** |
| **LTP / HanLP** | 没有时间归一化模块（NER 的「时间」只是实体识别），且模型过重（仓库 16.3 MB / 72.9 MB）。**不解决问题还背包袱** |

| **小米 duckling-fork-chinese** | Apache-2.0 许可干净，但 POM 依赖树含 scalaz / guava / kryo5 / **easy-bert**（排除 tensorflow 也没用）——对 minSdk 26 离线 App 是灾难。**只抄它的 `OpenIntervalValue` 与 `recentInFuture` 设计** |

| **Instructor / Outlines / Pydantic-AI / LangExtract / BAML** | 全是 Python 或 Rust 运行时。BAML 的 **Windows x64 原生包实测 58.6 MB**，且**没有 Android NDK 目标** |

| **向量数据库 / 端侧 NER（GLiNER / UIE / RNN 类）** | 与「离线轻量、无服务器」定位冲突。**这是旧版报告的争议项，本版裁决见第七节** |

**正确的借鉴姿势**：**确定性优先 + 交叉校验** —— 能确定性解的（金额归一、相对日期）本地解，**并用本地结果去校验模型输出**；只把真正需要语义理解的（这算不算「要去做」的事、这个称呼指谁）留给模型。本报告 P0-1（金额本地化）与 P0-2（日期交叉校验）就是这条分工落到两处最痛的地方。

**若确实想试某重型方案**：唯一现实路径是 **`tools/` 目录里的离线验证门禁** —— 把候选方案（如某个中文金额/日期解析器）装在 `tools/` 下（那里已有 Python 与 Node），用 P2-3 的 corpus 跑准确率，**覆盖率达到或超过现有 `LocalExtractor` 才考虑把规则（不是依赖）手工搬进 Kotlin**。**不许直接把依赖进主链路。**

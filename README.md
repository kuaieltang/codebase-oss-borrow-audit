# codebase-oss-borrow-audit · 代码库开源借鉴审计

> 一个 AI Agent 技能。读完你的代码库，对标开源项目，产出一份 **P0/P1/P2 分级、每条落到具体文件行号** 的可借鉴清单 Markdown。

**核心立场：借思想，不借依赖。**

---

## 它解决什么问题

「我这个项目能从 XX 开源项目借鉴什么？」——这个问题通常得到三种不理想的答案：

| 常见结果 | 问题 |
| --- | --- |
| 一篇开源项目介绍 | 讲的是别人，不是你 |
| 一堆「业界最佳实践」 | 没有行号，无法落地 |
| 直接推荐引入某个库 | 没算体积、运行时和 License 的账，塞进项目就炸 |

这个技能把它变成一个**可执行、可验证、有取舍**的清单：先盘点你已经做对了什么，再找出真正能补上的缺口，同时明确挡掉那些「看起来很美、塞进项目就炸」的方案。

## 产出长什么样

七节固定结构，见 [`examples/随身记-开源借鉴建议.md`](examples/%E9%9A%8F%E8%BA%AB%E8%AE%B0-%E5%BC%80%E6%BA%90%E5%80%9F%E9%89%B4%E5%BB%BA%E8%AE%AE.md)（一个真实案例：Android 离线 App 的抽取链路审计）：

```
一、现状盘点：你已经做到什么程度     ← 先钉住已有能力，避免建议重写
二、开源项目速查表                  ← 项目 / 可借的思想 / 适配结论
三、分级建议（P0 / P1 / P2）        ← 每条固定四段：现状 → 缺口 → 改法 → 收益
四、⚠️ 不要照做的提醒               ← 否决表 + 正确的借鉴姿势
五、涉及文件清单                    ← 改动矩阵，便于排期
六、实施顺序表                      ← 顺序 / 改动面 / 依赖
七、附录：多来源结论对照（可选）      ← ✅采纳 / ⚠️降级 / ❌否决 + 折中路径
```

## 安装

把整个目录复制到你的 Agent 技能目录即可：

| 环境 | 路径 |
| --- | --- |
| QwenWork（Windows） | `%USERPROFILE%\.qwenworkcn\skills\codebase-oss-borrow-audit\` |
| QwenWork（macOS / Linux） | `~/.qwenworkcn/skills/codebase-oss-borrow-audit\` |
| 其他支持 SKILL.md 的 Agent | 对应的 skills 目录 |

```bash
git clone https://github.com/kuaieltang/codebase-oss-borrow-audit.git ~/.qwenworkcn/skills/codebase-oss-borrow-audit
```

## 用法

装好之后，直接用自然语言触发。三类典型场景：

**① 已有对标对象**

> 代码库 `D:\myapp` 的抽取链路，我想对标 GLiNER / duckling / Instructor。请实际读完这条链路的关键源码，先说我哪里已经做对了，再给一份分级（P0/P1/P2）的可借鉴清单，每条落到具体文件行号，最后输出成 MD。

**② 没有对标对象**

> 代码库 `D:\myapp` 里的抽取模块我想对标开源，但还没想好对标谁。请先给我 2–3 个可比的开源候选，我确认后你再去读源码出清单。

**③ 引入决策**

> `lib/llm.js` 里的字段定义和解析器经常漂移。对标 Instructor / Outlines / BAML / DSPy，给我一份「借鉴思想、不引新依赖」的分级建议。

### 配套探针脚本

读代码前先定位，避免全仓通读烧掉上下文：

```bash
python scripts/probe_repo.py /path/to/repo --top 20 --tree-depth 3
```

输出三节：LOC 排行（代码沉在哪）、目录树（项目形状）、核心链路候选文件（带行号样例）。纯标准库、只读，支持 `--ext .kt` 收窄。

## 目录结构

| 文件 | 说明 |
| --- | --- |
| `SKILL.md` | 技能主文件：工作流、分级标准、硬约束、失败模式、交付自检 |
| `grading-rubric.md` | 五道否决闸（运行时/体积/License/保鲜/可逆性）+ 三级门槛 + 写作规格 |
| `template.md` | 输出 MD 的骨架，小节顺序固定 |
| `scripts/probe_repo.py` | 只读探针，纯标准库 |
| `.skill-metadata.yaml` | 4 条双语推荐 query |
| `examples/` | 真实产出样例 |

## 三条设计原则

1. **先盘点，再建议。** 没搞清你已经做对了什么就提建议，等于让你重写自己写好的东西。已被判定为「做对了」的能力不再作为借鉴项出现。
2. **每条都要有成本证据。** 只讲优点不讲体积/运行时/License 的建议，是把选型风险推给你。缺成本证据一律降级或删除。
3. **综合是解冲突，不是投票。** 多来源结论用对照表显式解冲突，少数派意见单列保留，不被平均掉。

### 运行时红线

离线 / 无服务器 / 移动端 / 控包体积的项目，**不得**为借鉴某算法把重型 Python（numpy/pandas/torch）、Haskell、JVM、需本地编译的工具链当作**运行时**依赖引入。三条替代路径：构建期或离线预处理、移植核心算法的轻量实现、改用平台原生能力。
